## 1. ゲーム概要

- **ジャンル**：装備で育てる2D横スクロールアクション（プラットフォーマー）。マリオ系。RPGではない（経験値・レベルは無い。強化はコイン→ショップの装備購入）。
- **対象**：子ども（W1〜W3は小学校低学年でもクリアできる易しさが要件）。
- **技術**：Canvas 2D＋Web Audio API＋localStorage。フレームワーク・ライブラリ・サーバー・API接続なし。**単一HTMLファイルが配布物そのもの**。
- **看板機能「マイヒーロー」**：顔写真をアップロードして自分をキャラ化できる。
- **長期構想**：App Store（Capacitorラッパー）と Web/PWA（NFT/ウォレット系）の2路線。収益化後にUnity移行を検討。

## 2. アーキテクチャ地図（名前参照）

### 全体構造
- CSS → 静的HTML → 巨大な `<script>`（IIFE・strict）。トップレベル関数はIIFE内 `try{}` の中にある。

## 4. 絶対に踏んではいけない地雷

-1. **`#overlay.scrollable` の直下の子から `flex-shrink:0` を外さない（v269）。** overflow:hidden な子は flex の最小サイズ保護が外れ、収まらない分その子だけが潰れる上に、潰れて収まるためスクロールも発生しない。実測: 性別選択のマイヒーロー枠が31px、ショップの剣リストが約90pxまで潰れた。
-2. **スクロールする画面のボタンで `touchstart` + `preventDefault()` をしない（v276）。** iOSはそれでスクロール操作そのものが死に、さらにドラッグしただけでボタンが発火する。タップは `_csTap` のように「移動8px未満のとき touchend で発火」にする。当たり判定が画面の大半を覆う「1枚絵＋透明ボタン」方式では致命的になる。
0. **`#overlay` に `min-height:100vh` を足さない。** `position:fixed;inset:0` で高さは既に確定していて、iOS の `100vh` は「ツールバーが隠れた時の高さ」＝実際の可視領域より大きい。両方効くと器が窓より高くなり、はみ出した分だけスクロール量が削られる。実測（390×674・vhを111%相当に膨らませた条件）でスクロール量 162px→88px、720px級の画面は **0px＝完全にスクロール不能**。v268で撤去。
1. ホーム画面に絵を足すとき `.home-btns` の流れに置かない（ロゴ585pxで画面外に落ちる）。`#overlay` 直下の絶対配置＋vh制限。
2. ロゴ画像の部分加工はしない（2回試して2回不採用）。
3. 持続的な位置アニメは3px/s未満にしない。
4. ホームのマークアップ2箇所同期（静的側とJS注入側）。
5. 新しい id/class/keyframes は使用前に grep 0件確認。
6. 画面遷移するボタンの演出DOMは `#overlay` 配下に置かない（`ov.innerHTML` ごと消える）。`document.body` 直下＋fixed。
7. `mix-blend-mode` は通常合成に置き換えられないことがある（multiplyは常に暗く、通常合成は明るくもなる）。
8. `lvCfg` の値が実際には誰にも読まれていないことがある。**難易度パラメータを信じる前に、その名前を grep して読まれている場所を確認**（例：`shootInterval` は死にパラメータ。生成側 `isShooter?110:isFire?80:0` がハードコード）。
9. スケール置換では「数・サイズ」と「種類の解禁」を分けて考える（閾値解禁は一段飛ばすと質的にジャンプする）。
10. 落下・接触など**新しいダメージ源は必ず `takeDamage()` 経由**。
11. iOS Safariのメモリ制約：base64画像を同時に増やしすぎるとモバイルで読み込み失敗する。埋め込み画像数は管理する。

- **埋め込み画像の内訳（v291実測）**：ファイル1,788,568Bのうち画像 約1.27MB（71%）／コード 約520KB（29%）。
  内訳は 大きいJPEG4枚（ホーム262KB・キャラ選択①232KB・マイヒーローのメニュー154KB・ワールド絵63KB）と
  PNG49枚。**PNGは顔8個を除いて256色に減色済み**（再度減色しても縮まない）。
  次に削るなら大きいJPEGの品質だが、これはユーザーが見た目を選んだ絵なので**要相談**。

- **`#overlay` の className は必ず明示代入する。** `classList.add/remove` だと直前の画面の
  `csbg` / `mhbg` / `hasnav` が残り、上下に見えない余白（77px・150px）が付いたまま出る。
  ★v292 で `showStageClear` / `showGameOver` / `showPauseMenu` / `confirmHome` を明示代入に修正した。
- **リザルト系は `#overlay.opaque`**（★v292）。既定の `#overlay` は不透明度0.95で、
  HUDの白文字が透けて読めてしまう。クリア／ゲームオーバーだけ不透明にしてある。

- **ステージ開始画面に「ボス」表記を出さない**（★v301で撤去）。全ステージにボスがいるので情報量がゼロで、逆に「このステージだけ特別なのか？」と紛らわしかった（実機で指摘）。
  `SFX.bossRoar()` の音は残してある（演出として機能しているため）。

### 8-4. 顔と体の馴染ませ（v303・実装済み／実機未確認）

§8-2 の最後の穴（「顔写真だけライティングなし」）を埋めた。処理は**顔の読み込み時に1回だけ**で、描画ループには何も足していない。

顔をロードする経路は3本（起動時の旧キー `yk_custom_face` 移行／`activateCustom` でのヒーロー切替／クロップ確定）。**3本とも `applyCustomHead` を通す**。増やすときも必ずここを通すこと。

- **① 体の肌色を写真から採る（`_ccPickSkin`）**
  128pxに正規化した顔の「ほお・鼻すじ」11点を8×8パッチで平均し、R/G/Bそれぞれの**中央値**を採る。
  目（相対y≒0.47）と口（≒0.72）と髪を外した帯だけを見ている。
  除外条件は3つ：アルファ<200（背景除去済みの外）／輝度<40 or >245（影・髪・白飛び）／**青>赤**（肌ではない）。
  有効サンプルが3点未満なら `null` を返し、従来の `CUSTOM_SKIN_DEF`（`#e8b88a`）のまま。
  結果は `CHARS.custom.skin` に入れるので、`drawStick` の首・手と `drawCharPreview` の手が**自動で追従する**（描画側は無改造）。
  実測：合成テスト顔3種（明/中/暗）で**3種とも色距離0＝完全一致**。全面透明・真っ黒・真っ白・青一色・顔が画面外の5種は全て `null`（＝安全側）にフォールバック。メガネ＋ひげ入りでも正解の `#e0b088` を返した。
- **② 顔に体と同じ光を焼き込む（`_ccShadeHead`）**
  `globalCompositeOperation='source-atop'` なので**透明な背景には一切色が乗らない**（四角い影が出ない）。
  左上に暖色の光・右下に落ち影。単離実測で 左上/右下＝**1.131**。体の `cylGrad` は 2.13 なので、**顔は意図的にかなり浅い**（写真は既に自前の陰影を持っているため）。
  結果の canvas をそのまま `HEAD['custom']` に入れる。`drawImage` の引数は画像と同じなので描画側は無改造。
- コスト：+3,878バイト（1,798,046 → 1,801,924）。実行は顔1枚につき `getImageData` 11回＋`fillRect` 2回の**1回きり**。
- 対象は `custom` のみ。**プリセット8体には触れていない**（あの8体のパレットは頭部写真と一緒に設計されているため）。

### 8-5. 作成の伝え方（v304・実機テスト中）

**v303の実機で判明した本当の問題。** スクショの実測がこれ：

| 測ったもの | 値 |
|---|---|
| 主人公ぜんたい（剣を含む） | 45.3 × 58.0 CSS px |
| そのうち顔（髪の天〜えり） | **22.7 px** |
| 写真のうち「体」が占める割合 | **61%** |

写真が半身で切り抜かれていて、**ゲーム側のベクターの体（首・手）が写真の服に完全に隠れていた**。
v303（肌色の自動採取）が効かなかったのはこれが理由で、施策の失敗ではなく**対象が画面に出ていなかった**。

原因は切り抜きUI。枠がただの丸で、案内も「ドラッグで位置調整・スライダーで拡大縮小」＝**操作方法しか言っておらず、何を枠に入れるのが正解かを一言も言っていなかった**。
さらに確定画面のプレビューはゲームの1.75倍で出るので「ちゃんと顔が見えている」と思って進めてしまう。

**打った手は3つ（すべてコードのみ・画像ゼロ）**

1. **顔ガイド**（`_ccDrawGuide`）— 丸の中にあごの線・頭のあたり・目のたかさを描く。
   位置は `HEAD_META.custom` から計算するので、メタ値を変えればガイドも追従する。
   写真の上でも見えるよう全部**黒で裏打ち**してある。
   案内文も「かおを わくいっぱいに！／あごを きいろい せんに あわせてね」を先に出し、操作方法は小さく下へ。
2. **等倍プレビュー**（`_CC_GAME_SCALE`）— 確定画面に「ゲーム中のおおきさ」を並べる。
   ⚠ `drawCharPreview` は頭部写真を切らないが `drawStick` は肩で切るので、**そのままでは見本が嘘になる**。
   第8引数 `clipHead` を足して等倍プレビューだけ `drawStick` と同じ切り方にした（キャラ選択の見た目は不変）。
3. **背景除去の結果を伝える**（`_ccPendingSilhouette`）— 成否は `_ccRemoveWhiteBg` が返していたのに
   ユーザーには何も言っていなかった。失敗時は「しろい かべの まえで とると もっと きれいになるよ」まで出す。

**実測（ヘッドレス）**
- ハーネスが実機の実測（顔22.7px）を **21px で再現**できたので出力を信用してよい（CLAUDE.md §1-8）
- ガイドどおりに切ると 顔 **21px → 29px（1.38倍）**。ベクターの体も画面に出るようになる

### 8-6. 背景除去の限界と、その回避（v304b・実機テスト中）

実機で「背景削除されてへん」。`_ccRemoveWhiteBg` を4パターンで実測した結果：

| 写真のタイプ | 結果 |
|---|---|
| ① 白かべ（無地） | ✅ 成功（不透明 100% → 30.8%） |
| ② **iPhoneの「被写体を切り抜く」PNG** | ✅ **素通しで完璧**（30.9% → 30.9%） |
| ③ 部屋で撮った（壁＋家具＋影） | ❌ 失敗 → フォールバック |
| ④ 暗い部屋（髪と背景が近い） | ❌ 失敗 → フォールバック |

**バグではなく仕様の限界。** 四隅の色のブレが46を超えたら「実写風景」と判断して除去しない設計で、
これは顔を食うリスクを避けるための意図的なゲート（§8-1）。部屋で撮った写真は原理的に通らない。

**②の経路は v209 から実装済みだったのに、アプリ内でその方法を一度も案内していなかった。**
Appleの切り抜きは自前のどんなアルゴリズムより精度が高いので、ここが最善の道。

**打った手は3つ**

1. **透明を含む画像はPNGで縮小する**（`_ccHasAlpha`）— ⚠ これが無いと②は永久に動かない。
   長辺1024px超の写真は縮小時に `toDataURL('image/jpeg',0.9)` で焼き直していたが、
   **JPEGには透明が無い**ので切り抜きが潰れていた。iPhoneの写真は普通3000px超なので必ずこの経路を通る。
   実測（実際のファイル選択経由・2000px）：透明あり → `data:image/png;base64,` ／ 不透明 → `data:image/jpeg;base64`。
2. **iPhoneの切り抜きを案内する**（写真選択画面の「✨ はいけいを けしたいとき」3ステップ、
   および背景除去に失敗したときのメッセージ）。写真選択画面は `overflow:hidden` でスクロールできないので、
   追加前に余白を実測した：**もどるボタンの下端 414px → 522px、iPhone SE(548) でも 26px 残る**。
3. **丸マスクを頭のかたち（たまご型）にする**（`CC_EGG`）— ①②が効かなかったときの受け皿。
   形だけで切るので必ず効く。保存される顔の不透明域は **丸 78.5% → たまご 50.0%（面積 -36.3%）**。
   ガイドのたまご（rx=72/ry=88）より一回り大きくしてあるので、髪が多少はみ出しても切れない。

**未検証（実機でしか分からない）**
- 🔴 iOSのファイル選択でPNGの透明が保たれるか（iOSがHEIC/JPEGに変換してしまう可能性がゼロではない）
- たまご型で髪の横が切れる人がいないか

## 12. 盾ガードの仕様（v305で統一・実機テスト中）

**どのダメージを防げるか**（コードを全数確認した結果）

| ダメージ源 | 盾で防げる | 実装箇所 |
|---|---|---|
| 弾（火の玉・レーザー・氷・闇など） | ✅ | 弾のプレイヤー命中判定 |
| 敵の体当たり・突進・接触 | ✅ | `guardingBody` |
| トゲ敵を踏んだとき | ❌ | 踏みつけ分岐にガード判定なし |
| 爆弾の爆風 | ❌ | コードに「防御不可」と明記 |
| 覚醒ボスのブレス | ❌ | ブレス判定にガードなし |
| 落下ダメージ | ❌ | `takeDamage(40,{label:'落下!'})` |

**v305で直したこと**

1. **条件の食い違い**：弾だけ `(gG()||p.guardHold>0)&&hasSk(3)`、体当たりは `p.st==='guard'` で見ていた。
   `p.st` は「攻撃中→`atk`」が先に評価されるため、**剣を振っている最中は「弾は防げるのに体当たりは食らう」**状態だった。
   両方を `p.st==='guard'` に統一し、「攻撃と防御は同時にできない」に揃えた。
   なお体当たりガード自体は v236 から入っている（それ以前は防げなかった）。
2. **進行不可**（`GUARD_SPD=0`）：進みながら構えると弾も体当たりも防げて実質無敵だったため、
   盾を「止まって守る」構えにした。

**実測（実機と同じキーボード操作で60フレーム入力）**

| 入力 | 移動距離 | `p.st` |
|---|---|---|
| → だけ | 252.3px | `run` |
| → ＋ガード | **0px** | `guard` |
| ← ＋ガード | **0px** | `guard` |
| ガード解除後に → | 252.3px | `run` |

ガードのみ → `st=guard`（弾も体当たりも防げる）／ガード＋攻撃 → `st=atk`（どちらも防げない）。
⚠ 対照群：ガードを一切使わずに → を4回繰り返すと 252.3 / 175.2 / 252.3 / 179.6px とばらつくが、
**短い回はHPが減っている＝敵のノックバック**。ガードによる残留スローダウンではない。

### 8-7. iPhoneの「被写体を切り抜く」が実機で通った（v307で仕上げ）

2026-09-26、実機で初めて成功。確定画面に「✅ はいけいを きれいに けせたよ」が出た。
**iOSのファイル選択はPNGの透明を保ったまま渡してくれる**（§8-6 の🔴が解消）。
手順は **写真アプリで人を長押し → 「共有…」→「画像を保存」→ それをえらぶ**。
⚠ 長押しのメニューに「保存」は無い（「コピー／ステッカーに追加／**共有…**」の3つ）。
v304bの案内は「ほぞん」と書いていて実物と合っていなかった → **★v308で修正済み**（下記）。

**そのとき出た2つの問題と対処**

1. **枠外の身体まで拾う** — たまご型のトリムを「背景除去に失敗したときだけ」掛けていた。
   iPhoneの切り抜きは**必ず成功する**側に入るので、切り抜かれた人物まるごと
   （頭＋肩＋服）が「頭」として描かれていた。
   → **成否にかかわらず必ず掛ける**ようにした。アルファを下げるだけなので
   すでに透明な部分はそのまま＝たまごとの交差になる。
   実測（ガイドどおりに枠取り・切り抜き済み人物）：
   **あごより下に残る画素 5,059 → 306（94.0%減）／不透明 46.9% → 39.7%**
2. **確定画面の「もどる」が写真選択の前まで戻る** — 顔の調整をやり直せなかった。
   原因は、切り抜き確定の時点で `_ccImg=null`（メモリ解放）していたこと。
   → 解放を**フローを抜けるとき**に移し、「もどる」は調整画面へ戻すようにした。
   `_ccImgX/_ccImgY/_ccZoom/_ccBaseScale` はトップレベル変数なので位置と拡大率は保持される。

## 9. ④星評価の調査結果（2026-08-13・調査のみ／コード未変更）

### 9-1. 判定式（`nextLevel` 内）

```
killRate = stageEnemyKilled / stageEnemyTotal   （重み 0.50）
coinRate = stageCoinGot     / stageCoinTotal    （重み 0.25）
hpRate   = p.hp / p.maxHP                       （重み 0.25）
stageScore = min(1, 上記の合計)
★3 = 0.85以上 / ★2 = 0.60以上 / ★1 = クリアのみ
```

分母は `doStart` が `buildWorld` 直後に確定（`cins.length` と `enms` の非ボス数＋ボス1）。

### 9-2. カウンタ側は健全（＝バグではない）

- `enms.splice` **0件**。敵は画面外でも配列から消えない → 分母は減らない
- `maybeDrop` はハート（giant限定）のみ。コイン加算は `cins` ループの1箇所だけ → `coinRate` が1を超える経路なし
- ボス撃破は `onBossDefeated` の `bossDefeated` ガードで二重加算なし
- **結論：分子が分母を超える経路は存在しない。式の設計が原因。**

### 9-3. 原因3つ

**① HPが「見えない足切り」になっている（「出たり出なかったり」の主犯）**

| プレイ内容 | stageScore | 星 |
|---|---|---|
| 敵全滅・コイン40%・無傷 | 0.850 | ★3 |
| 敵全滅・コイン40%・HP80% | 0.800 | ★2 |

同じ立ち回りでも1回の被弾で★3→★2。しかも条件が画面に出ていない。

**② 序盤ワールドは敵が少なく判定が粗い**

`enemyN=round(4+d*40)`＋ボス1。ハーネスはコード内コメントの既知値6/6を再現（信用可）。

⚠ **この表はv258以前の古い値だった。2026-08-28に50回生成で実測し直した値が正**：

| W | 敵総数 | ★2に必要(50%) | ★3に必要(70%) | ★3の取りこぼし許容 |
|---|---|---|---|---|
| 1 | 12 | 6体 | 9体 | 3体 |
| 2 | 16 | 8体 | 12体 | 4体 |
| 3 | 22 | 11体 | 16体 | 6体 |
| 5 | 46 | 23体 | 33体 | 13体 |
| 10 | 157 | 79体 | 110体 | 47体 |

**敵の総数はプレイのたびにブレない**（50回とも同値）。v258の独立3条件になった今、
「序盤ほど神経質」は解消している（W1でも3体まで取りこぼせる）。

**③ コイン総数がプレイのたびにランダムに変動（「ほとんど★3」の一因）**

- 浮台コインは確率出現（通常台85% / 高台95%）
- 地面コインは穴の上ならスキップ、その穴位置もランダム
- → 同じステージでも分母が変わり、同じ枚数でも `coinRate` が変わる
- ★3に必要なコイン率は**40%だけ**（敵全滅・無傷時）。だから「敵を全部倒して無傷なら★3」が出やすい

### 9-4. 副次的な発見（実害小）

v231で `false` 固定になったため**現在は無効**。ボスは `GOAL_X-360`、撃破で自動クリアのため
その先のコインは取れない。ただし該当区間は約60px＝**コイン0〜1枚相当**で実害は小さい。

### 9-6. 実機で判明：クリア画面は「マップ選択プレイ」でしか出ない（2026-08-13）
