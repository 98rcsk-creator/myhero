## 1. ゲーム概要

- **ジャンル**：装備で育てる2D横スクロールアクション（プラットフォーマー）。マリオ系。RPGではない（経験値・レベルは無い。強化はコイン→ショップの装備購入）。
- **対象**：子ども（W1〜W3は小学校低学年でもクリアできる易しさが要件）。
- **技術**：Canvas 2D＋Web Audio API＋localStorage。フレームワーク・ライブラリ・サーバー・API接続なし。**単一HTMLファイルが配布物そのもの**。
- **看板機能「マイヒーロー」**：顔写真をアップロードして自分をキャラ化できる。
- **長期構想**：App Store（Capacitorラッパー）と Web/PWA（NFT/ウォレット系）の2路線。収益化後にUnity移行を検討。

## 2. アーキテクチャ地図（名前参照）

### 全体構造
- CSS → 静的HTML → 巨大な `<script>`（IIFE・strict）。トップレベル関数はIIFE内 `try{}` の中にある。
- ホーム画面のマークアップは**2箇所**：静的HTML（`#overlay` 直下）と JS注入（`showTitleScreen`）。同期必須（CLAUDE.md §2-2）。

## 4. 絶対に踏んではいけない地雷

-1. **`#overlay.scrollable` の直下の子から `flex-shrink:0` を外さない（v269）。** overflow:hidden な子は flex の最小サイズ保護が外れ、収まらない分その子だけが潰れる上に、潰れて収まるためスクロールも発生しない。実測: 性別選択のマイヒーロー枠が31px、ショップの剣リストが約90pxまで潰れた。
-2. **スクロールする画面のボタンで `touchstart` + `preventDefault()` をしない（v276）。** iOSはそれでスクロール操作そのものが死に、さらにドラッグしただけでボタンが発火する。タップは `_csTap` のように「移動8px未満のとき touchend で発火」にする。当たり判定が画面の大半を覆う「1枚絵＋透明ボタン」方式では致命的になる。
0. **`#overlay` に `min-height:100vh` を足さない。** `position:fixed;inset:0` で高さは既に確定していて、iOS の `100vh` は「ツールバーが隠れた時の高さ」＝実際の可視領域より大きい。両方効くと器が窓より高くなり、はみ出した分だけスクロール量が削られる。実測（390×674・vhを111%相当に膨らませた条件）でスクロール量 162px→88px、720px級の画面は **0px＝完全にスクロール不能**。v268で撤去。
1. ホーム画面に絵を足すとき `.home-btns` の流れに置かない（ロゴ585pxで画面外に落ちる）。`#overlay` 直下の絶対配置＋vh制限。
2. ロゴ画像の部分加工はしない（2回試して2回不採用）。
3. 持続的な位置アニメは3px/s未満にしない。
4. ホームのマークアップ2箇所同期（静的側とJS注入側）。
5. 新しい id/class/keyframes は使用前に grep 0件確認。
6. 画面遷移するボタンの演出DOMは `#overlay` 配下に置かない（`ov.innerHTML` ごと消える）。`document.body` 直下＋fixed。
7. `mix-blend-mode` は通常合成に置き換えられないことがある（multiplyは常に暗く、通常合成は明るくもなる）。
8. `lvCfg` の値が実際には誰にも読まれていないことがある。**難易度パラメータを信じる前に、その名前を grep して読まれている場所を確認**（例：`shootInterval` は死にパラメータ。生成側 `isShooter?110:isFire?80:0` がハードコード）。
9. スケール置換では「数・サイズ」と「種類の解禁」を分けて考える（閾値解禁は一段飛ばすと質的にジャンプする）。
10. 落下・接触など**新しいダメージ源は必ず `takeDamage()` 経由**。
11. iOS Safariのメモリ制約：base64画像を同時に増やしすぎるとモバイルで読み込み失敗する。埋め込み画像数は管理する。

- **埋め込み画像の内訳（v291実測）**：ファイル1,788,568Bのうち画像 約1.27MB（71%）／コード 約520KB（29%）。
  内訳は 大きいJPEG4枚（ホーム262KB・キャラ選択①232KB・マイヒーローのメニュー154KB・ワールド絵63KB）と
  PNG49枚。**PNGは顔8個を除いて256色に減色済み**（再度減色しても縮まない）。
  次に削るなら大きいJPEGの品質だが、これはユーザーが見た目を選んだ絵なので**要相談**。

- **`#overlay` の className は必ず明示代入する。** `classList.add/remove` だと直前の画面の
  `csbg` / `mhbg` / `hasnav` が残り、上下に見えない余白（77px・150px）が付いたまま出る。
  ★v292 で `showStageClear` / `showGameOver` / `showPauseMenu` / `confirmHome` を明示代入に修正した。
- **リザルト系は `#overlay.opaque`**（★v292）。既定の `#overlay` は不透明度0.95で、
  HUDの白文字が透けて読めてしまう。クリア／ゲームオーバーだけ不透明にしてある。

### 8-1. 顔ハメ白背景バグ（v235で対策済み・実機未確認）
- 症状：顔写真の白背景ごと丸く切り抜かれて表示される。原因：`_ccRemoveWhiteBg` が false → 円形クロップにフォールバック（白は保存PNGに焼き込まれる）。
- 切り分け結果：同じ画像で切り取り位置を極端に振っても成功 → **犯人は画像の背景の質**。v235でプロンプト側を修正した。
- **再発したときの控えの策（案A）**：円クロップ後に、円周のすぐ内側のリングから背景色を採り直し、縁から内向きにフラッドフィルで再除去。失敗時は現状の円クロップに戻す。
- 色距離の落とし穴：除去は背景色から距離52以内を背景扱い。肌 `#F5E0D0` は距離57.2で**余裕5しかない**。明るい肌 `#FAEDE3` は33.7で顔が食われる。プロンプトに「肌や髪を真っ白にしない」を入れてあるのはこのため。
- どの対策でも**登録済みの顔は直らない**（白ごと焼かれている）。登録し直しが必要。

### 8-2. 3DCG化の調査結果（全身の3D置き換えは却下）
- ゲーム中キャラの実データ量は**46×75px**（頭47px・体幅16px）。実機の見た目はここからの引き伸ばし。
- 現行キャラ**1.34頭身**に対しAI生成フィギュアは**3.06頭身**。同じ枠に入れると顔が22pxに潰れる。
- 体をプリレンダー画像化すると `ch.body[lv]` / `getOutfitSkin` の**色替え＝装備で育つ仕組みが死ぬ**。
- **結論：3Dの投資先は「顔の質」と「大きく見せる画面」**（編集画面・ホーム）。
- 疑似3Dは既に半分入っている（`sphGrad`/`shade`/`hairGrad`/`hairGloss`）。**穴は `drawStick` の顔写真だけ**（ライティングなし・体との質感差の原因）。20〜30行で埋まる見込み。
- WebGL/three.js は0件。単一ファイル制約とプレイ中32.8fpsから実行時3Dは割に合わない。

### 8-3. キャラ作成導線（方針転換・合意済み）
- 現行AIキャラ化は**2アプリ7ステップ**。AIアプリを持たない人は0歩目で脱落。
- **最重要要件：AIやPCが苦手な人でもオリジナルキャラを作れること。** 3DCG感はユーザー作業でなくレンダラー側に埋め込む。
- 入口4層：①プリセット8体 ②**タップで作る色・髪型エディタ（本命・未実装）** ③写真で顔だけ自分 ④AI似顔絵（上級者向けに格下げ）。
- 層②に必要なのは色送りUI（7スロット）と1色→6段グラデ生成のみ。レンダラー側は完成済み。新規画像ゼロ・APIゼロ。

## 9. ④星評価の調査結果（2026-08-13・調査のみ／コード未変更）

### 9-1. 判定式（`nextLevel` 内）

```
killRate = stageEnemyKilled / stageEnemyTotal   （重み 0.50）
coinRate = stageCoinGot     / stageCoinTotal    （重み 0.25）
hpRate   = p.hp / p.maxHP                       （重み 0.25）
stageScore = min(1, 上記の合計)
★3 = 0.85以上 / ★2 = 0.60以上 / ★1 = クリアのみ
```

分母は `doStart` が `buildWorld` 直後に確定（`cins.length` と `enms` の非ボス数＋ボス1）。

### 9-2. カウンタ側は健全（＝バグではない）

- `enms.splice` **0件**。敵は画面外でも配列から消えない → 分母は減らない
- `maybeDrop` はハート（giant限定）のみ。コイン加算は `cins` ループの1箇所だけ → `coinRate` が1を超える経路なし
- ボス撃破は `onBossDefeated` の `bossDefeated` ガードで二重加算なし
- **結論：分子が分母を超える経路は存在しない。式の設計が原因。**

### 9-3. 原因3つ

**① HPが「見えない足切り」になっている（「出たり出なかったり」の主犯）**

| プレイ内容 | stageScore | 星 |
|---|---|---|
| 敵全滅・コイン40%・無傷 | 0.850 | ★3 |
| 敵全滅・コイン40%・HP80% | 0.800 | ★2 |

同じ立ち回りでも1回の被弾で★3→★2。しかも条件が画面に出ていない。

**② 序盤ワールドは敵が少なく判定が粗い**

`enemyN=round(4+d*40)`＋ボス1。ハーネスはコード内コメントの既知値6/6を再現（信用可）。

| W | 敵総数 | 敵1体の重み | ★3まで許される取りこぼし（HP満・コイン満時） |
|---|---|---|---|
| 1 | 8 | 6.25% | 2体 |
| 2 | 10 | 5.00% | 3体 |
| 5 | 19 | 2.63% | 5体 |
| 10 | 53 | 0.94% | 15体 |

W1は1体で6.25%動く＝**序盤ほど神経質**という狙いと逆の設計。

**③ コイン総数がプレイのたびにランダムに変動（「ほとんど★3」の一因）**

- 浮台コインは確率出現（通常台85% / 高台95%）
- 地面コインは穴の上ならスキップ、その穴位置もランダム
- → 同じステージでも分母が変わり、同じ枚数でも `coinRate` が変わる
- ★3に必要なコイン率は**40%だけ**（敵全滅・無傷時）。だから「敵を全部倒して無傷なら★3」が出やすい

### 9-4. 副次的な発見（実害小）

`coinRange` の「ボス手前までにコインを配置」（`GOAL_X-420`）は `bossDensity` が
v231で `false` 固定になったため**現在は無効**。ボスは `GOAL_X-360`、撃破で自動クリアのため
その先のコインは取れない。ただし該当区間は約60px＝**コイン0〜1枚相当**で実害は小さい。

### 9-7. v258 の新ルール（実装済）

```
★1 = クリアする
★2 = てきを STAR_KILL2(50%) 以上たおす  または  コインを STAR_COIN(70%) 以上とる
★3 = てきを STAR_KILL3(70%) 以上たおし、かつ（コイン70%以上 または ノーダメージ）
```

閾値は `STAR_KILL2` / `STAR_KILL3` / `STAR_COIN` の3定数。**16パターンで新旧を照合し、
旧の合算式より厳しくなるケースが0件**であることを確認済み。

§9-3 の原因3つへの対応：
- ① HPの見えない足切り → **解消**。HPは★3の2つある道のうち片方でしかない
  （敵ぜんぶ＋コイン満なら HP30% でも★3。旧は★2だった）
- ② 序盤ほど神経質 → **緩和**。W1で5体のがしても★2（旧と同じ）
- ③ コイン分母のランダム変動 → **影響が小さくなった**。コインは★2・★3とも
  「もう一方の道」があるため、分母が揺れても星が揺れにくい

### 9-6. 実機で判明：クリア画面は「マップ選択プレイ」でしか出ない（2026-08-13）

`showStageClear` の呼び出しは `nextLevel` 内の **`if(fromStageMap)` の中に1箇所だけ**。
`fromStageMap` を true にするのは `startStageFromMap` と クリア画面の「つぎへ すすむ」の2箇所で、
`startFromTitle`（ホームの「タップしてスタート」）は立てない。
このため**連続プレイではクリア画面が一度も出ず、そのまま次ステージへ直行する**（v237の表示も見えない）。

**★の付与自体は正常**：`setStageStar(level, earnedStar)` は `if(fromStageMap)` より**手前**にあるため、
遊び方に関係なく毎ステージ保存される（`yk_stars`）。ステージマップのカードと `totalStars()` に反映される。

→ **v239 で案A（結果画面を出す）を採用・実装済み**（実機未確認）。

**実装上の注意（重要）**：`doStart` の1行目は `level=fromStageMap?selectedStage:1; score=0;` で
**score を 0 にリセットする**。そのためクリア画面の「つぎへ すすむ」から `doStart` を通すと
連続プレイのスコアが毎ステージ 0 に戻ってしまう。v239 では `nextLevel` の後半を `advanceStage()` として
関数化し、連続プレイの「つぎへ」はそちらを呼ぶことで score とラン継続性を維持している。
`_contAdvancePending` がその分岐フラグ（「ステージをえらぶ」「ホームにもどる」で解除される）。

ラン単位の仕様は据え置き：`addRanking` はラン終了時（ALL CLEAR／死亡）のみ。
コインは連続プレイでもステージごとに貯金するよう変更したが、**死亡時も貯金される仕様のため合計額は不変**。
